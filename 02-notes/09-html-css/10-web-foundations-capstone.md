# HTML/CSS checkpoint — independent accessible interface

## Brief

After both web labs, build a small static interface from a new brief: an equipment directory, event schedule or learning-resource page. Do not merely recolor the reference. Use semantic content, a meaningful table/list where appropriate, a usable native form and a layout justified by the content.

## Acceptance evidence

- Complete document, meaningful title/language, logical headings/landmarks and valid label relationships.
- Correct asset/navigation URLs; only deliberate public assets are served.
- Responsive behavior with content changes, intermediate widths, long text and enlargement; no hidden essential content.
- Visible keyboard focus, native interaction and meaningful validation feedback.
- Appropriate alternatives/contrast and an honest manual accessibility record, not an automated-score certificate.
- CSS rules/components you can explain through the cascade and box/layout model.

Write a short design/structure explanation and a defect report with before/after evidence. Mark unperformed assistive-technology/browser checks explicitly.

## Independent change request

Add a new form field and a longer translated heading, then support an optional sidebar. Preserve submitted names, logical order, readable content and keyboard operation. Update checks/manual evidence before claiming completion.

## Toward fullstack

Next use the existing JavaScript track to add behavior/state and an API client. Then connect a FastAPI backend with explicit validation, ownership and failure contracts. Do not insert user content through unsafe HTML or assume client validation secures the server.

Use [[web-app-structure]] to choose a static-site versus integrated app boundary. Frameworks can follow when you understand the mechanism they simplify.
